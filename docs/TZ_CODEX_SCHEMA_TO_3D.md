# ТЗ для Codex: «Схема → реальная 3D-площадка»

Проект «СМЕНА» — обучающий 3D-тренажёр для аппаратчиков УПЭ по производственной
инструкции № 408-Р-6. Уже работает: страница `/sim` (Three.js, вид от первого лица,
WASD/тач), два режима — «Тревоги смены» (реальные отклонения из Табл. №12) и
демо-пуск насоса. Сейчас планировка площадки захардкожена в коде и расставлена
приблизительно. **Твоя задача — сделать планировку данными и приводить её в
соответствие со схемами установки, которые я буду добавлять в репозиторий.**

## 0. Репозиторий и запуск

- Репо: `https://github.com/Nodensss/Instrukciya.git`, ветка **`claude/smena-project-setup-swxwxn`**
  (работай в ней же; коммиты с понятными сообщениями).
- Запуск: `npm install && npm run dev` → http://localhost:3000/sim
- Проверка: `npm run build` обязан проходить перед каждым коммитом.
- Стек: Next.js 15 (App Router) + TypeScript + Tailwind 4 + three (npm-пакет, без CDN).

Ключевые файлы:

| Файл | Что это |
|---|---|
| `components/PumpWalkSim.tsx` | Вся 3D-сцена и оба режима игры |
| `content/deviations.json` | Канонический контент Табл. №12 (52 записи, в игре только `status:"ok"`) |
| `lib/deviations.ts` | Чтение/фильтрация контента |
| `app/sim/page.tsx` | Серверная страница, передаёт отклонения в компонент |
| `PROJECT_BRIEF_SMENA.md` | Общий бриф проекта |

## 1. Этап 0 (сделать один раз): планировка как данные

Вынести всю геометрию площадки из `components/PumpWalkSim.tsx` в файл
**`content/plant-layout.json`** и написать билдер, который строит сцену из него.

### 1.1. Формат `content/plant-layout.json`

```jsonc
{
  "meta": {
    "source": "описание/имя схемы, по которой сделана планировка",
    "updated": "2026-07-07",
    "units": "метры, ось X — восток, Z — юг (как сейчас в сцене), Y — вверх",
    "note": "планировка условная, уточняется по схемам из docs/schemas/"
  },
  "bounds": { "minX": -15, "maxX": 15, "minZ": -14.5, "maxZ": 15 },
  "playerStart": { "x": 0, "z": 9, "yaw": 0 },
  "equipment": [
    {
      "id": "reactor",              // уникальный id
      "type": "column",             // тип префаба, см. 1.2
      "x": -6.5, "z": -12.5,
      "rotY": 0,                    // поворот в радианах, опционально
      "label": "РЕАКТОР",           // табличка над объектом
      "labelHeight": 9.0,           // высота таблички, опционально
      "params": { "r": 1.3, "h": 7.5 },  // параметры префаба
      "collider": 1.8,              // радиус коллизии; 0 или нет — проходимый
      "anchorGroup": "reactor",     // куда ведёт маяк тревог этой группы (см. 1.3)
      "anchorRadius": 3.4           // радиус срабатывания «дошёл»
    }
  ],
  "pipes": [
    // полилиния трубы по точкам (y — высота), r — радиус трубы
    { "r": 0.13, "points": [[ -9, 0.75, -2 ], [ -2.7, 0.75, 0 ], [ 0, 0.75, 0 ]] }
  ],
  "decor": [
    // необязательные элементы антуража тем же форматом, что equipment
  ]
}
```

### 1.2. Библиотека префабов (минимальный набор)

В билдере реализовать функции-префабы (низкополигональные, из боксов/цилиндров/торов,
материалы взять существующие из компонента):

| type | Описание | params |
|---|---|---|
| `column` | вертикальный аппарат с юбкой, фланцами, кольцевой площадкой | `r, h` |
| `tank_vertical` | вертикальная ёмкость с обвязкой-поясом | `r, h` |
| `tank_horizontal` | горизонтальный аппарат на сёдлах (испаритель и т.п.) | `r, len` |
| `pump` | насосный агрегат на раме (улитка + двигатель) | `scale?` |
| `compressor` | компрессорный агрегат | — |
| `cooler_bank` | этажерка горизонтальных холодильников | `rows?` |
| `valve_manual` | задвижка со штурвалом на стойке | — |
| `valve_control` | регулирующий клапан с сервоприводом («Böhler») | — |
| `console` | пульт/ЦПУ с экраном-мнемосхемой | `w?` |
| `sensor_post` | датчик на стойке (ДВК и т.п.) | — |
| `rack` | эстакада трубопроводов (сегмент по длине) | `len, tiers?` |
| `platform` | площадка с ограждением и лесенкой | `w, d, h` |
| `mast` | прожекторная мачта с источником света | — |
| `fence_ring` | кольцевое ограждение зоны | `r, gapDeg?` |

Новые типы добавлять по мере надобности схем — это нормальный путь расширения.
Каждый префаб обязан отбрасывать/принимать тени и укладываться в общий стиль
(тёмный графит, сталь, латунно-жёлтые пояса, статусные цвета — константы `C` в компоненте).

### 1.3. Что билдер делает автоматически

- **Коллайдеры**: из поля `collider` каждого элемента (круг в плане).
- **Якоря тревог**: собрать `ANCHORS` из элементов с `anchorGroup` —
  это привязка групп отклонений Табл. №12 (`kip, pumps_general, propan, reactor,
  gas, nmpe, bohler, dosing, oil, hot_water, safety`) к точкам площадки.
  **Каждая из 11 групп обязана иметь ровно один якорь** — билдер должен валидировать
  это на старте и падать с понятной ошибкой, если группа не покрыта.
- **Таблички**: `label` → канвас-спрайт (функция `makeLabelSprite` уже есть).
- **Границы ходьбы**: из `bounds`.

### 1.4. Критерий готовности этапа 0

- Текущая площадка воспроизведена из `plant-layout.json` (можно с точностью
  «на глаз», позиции те же).
- Оба режима работают как раньше: тревоги ведут к правильным аппаратам,
  демо-пуск Н-101 проходится (его интерактивные точки ЗД-101/ЗД-102/PI-101/МП-101/
  маслобак могут остаться в коде — это отдельный слой поверх layout).
- `npm run build` зелёный.

## 2. Рабочий цикл «схема → планировка» (повторяется на каждую схему)

Я кладу схему в **`docs/schemas/`** (скан плана/технологической схемы из
инструкции, фото от руки или текстовое описание). Далее ты:

1. **Разбор схемы.** Составь таблицу: позиция (обозначение), тип оборудования,
   координаты на плане (в метрах, привяжи масштаб к чему-то известному на схеме;
   если масштаба нет — прими шаг сетки и напиши допущение), ориентация.
2. **Покажи таблицу мне на подтверждение** (в PR-описании или комментарии),
   с перечнем допущений. Не начинай строить, пока таблица спорная — спроси.
3. **Обнови `content/plant-layout.json`**: позиции, подписи, трубы, якоря групп.
   Если нужного префаба нет — добавь новый тип в билдер.
4. **Проверь сборку и сделай скриншоты** (см. §4) с 3–4 ракурсов, приложи к PR/коммиту.
5. Коммит: `layout: <имя схемы> — что изменилось`.

## 3. Жёсткие правила (нарушать нельзя)

1. **Контент**: `content/deviations.json` не редактировать вообще (тексты дословные
   из инструкции). Механику квизов, подсчёт очков, экраны — не менять без отдельной задачи.
2. **Подписи оборудования** — только реальные обозначения со схемы/из инструкции
   (А-401, А-503, А-507, А-315/316/322/325 и т.д.). Ничего не выдумывать; если на
   схеме позиции нет — подпись типа «НАСОС» без номера.
3. Демо-контур пуска Н-101 остаётся и остаётся помеченным «ДЕМО».
4. Дисклеймеры в меню не убирать. Robots noindex не трогать. Публичных деплоев не делать.
5. Стиль «ЦПУ» сохранять: палитра `C`, моно-теги, никакой посторонней цветастости.
6. Мобильное управление (джойстик/свайп/«ДЕЙСТВИЕ») должно продолжать работать.
7. `npm run build` перед каждым коммитом. Ломаешь — чинишь до коммита.
8. Не добавлять тяжёлых зависимостей (GLTF-модели, физдвижки, ассеты >200 КБ) без согласования.

## 4. Как проверять визуально (headless-скриншоты)

В сцене есть отладочный хук `window.__simDebug.set(x, z, yaw)` — телепорт камеры.
Скрипт для скриншотов (playwright-core + системный Chromium):

```js
import { chromium } from "playwright-core";
const b = await chromium.launch({ args: ["--use-gl=swiftshader","--enable-unsafe-swiftshader"] });
const p = await b.newPage({ viewport: { width: 1280, height: 800 } });
await p.goto("http://localhost:3000/sim", { waitUntil: "networkidle" });
await p.click("text=ТРЕВОГИ СМЕНЫ");           // войти в режим ходьбы
await p.evaluate(() => window.__simDebug.set(0, 10, 0));   // точка обзора
await p.screenshot({ path: "shot-1.png" });
await b.close();
```

Обязательные ракурсы после каждого изменения планировки: общий вид от старта,
каждый новый/перемещённый аппарат крупно, вид вдоль главной оси.

- [ ] Все 11 групп тревог покрыты якорями, валидатор молчит
- [ ] Скриншоты приложены
- [ ] `npm run build` зелёный, оба режима проходятся
- [ ] Коммит(ы) в ветку `claude/smena-project-setup-swxwxn` запушены

## 6. Чего НЕ делать

- Не переписывать проект на другой фреймворк/движок (React Three Fiber, Babylon и т.п.).
- Не менять структуру `deviations.json` и логику `/play`.
- Не оптимизировать преждевременно (инстансинг, LOD) — пока сцена лёгкая.
- Не деплоить и не создавать публичных ссылок: документ внутренний.
